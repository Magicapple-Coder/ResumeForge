# Prompt 调参指南

所有提示词模板集中在 `backend/app/prompts/`，与业务代码完全分离——改模板不需要动代码。

## 模板清单

| 文件 | 作用 | 何时调整 |
| --- | --- | --- |
| `resume_generate_system.md` | 系统提示词：角色设定与全局规则（真实性、岗位匹配/全貌优先、事实锚定、成果量化、措辞标准、篇幅与粒度、分模块呈现要求、输出格式）。**Jinja 模板**，见下方说明 | 生成质量、防虚构约束、措辞与篇幅口径 |
| `resume_generate_user.md` | 用户提示词：岗位候选资料 + JD + 美化拓展边界 + JSON 结构示例 | 结构字段、JD 使用方式、分级拓展策略 |
| `resume_quality_retry.md` | 深度美化质量重试：根据具体短板重新生成完整 JSON | 附件项目内容过少、照抄原文或描述/亮点分配不合理时 |
| `resume_fix_json.md` | JSON 修复提示词 | 模型输出 JSON 经常失败时 |
| `job_text_extract.md` | 岗位粘贴文本的结构化字段抽取 | 职位、公司、职责、要求或其他信息分区不准确时 |
| `profile_text_extract.md` | 个人资料粘贴文本的结构化字段抽取 | 教育、经历、项目、技能或奖项分区不准确时 |
| `image_extraction_addendum.md` | 图片识别的补充要求：先逐字抄录再抽字段；**追加**在上面两个模板之后，不单独使用 | 截图抄录漏字、字段常被判为无依据时 |

### 简历生成 Prompt 现在带岗位分支

`resume_generate_system.md` 和 `resume_generate_user.md` 都用 `{% if job %}` / `{% else %}`
分支：有目标岗位走原来的岗位口径，没有岗位（通用简历）走"全貌优先"口径——不按方向筛选、
保留每个非空区块、个人总结不绑定岗位名、`job_intent` 沿用资料原文。

**系统提示词此前是纯文本直读，现在也走 Jinja 渲染。** 这意味着这个文件里的 `{{`、`{%`、`{#`
从此有语法含义：

- 写 `{{ 变量 }}` 而变量未提供 → `StrictUndefined` 直接抛错，整次生成失败；
- 写 `{% ... %}` → 会被当作标签处理，可能静默吞掉正文。

所以**不要在这个文件里写包含大括号的示例**（比如贴一段 JSON 片段）。改完请跑
`tests/test_resume_generator_validation.py` 里的两分支渲染用例。

**改这两个文件时先渲染再 diff。** 用同样的 job 与资料（有岗位、无岗位各一次）分别渲染新旧模板，
确认差异只有你有意改的那几行——`{% if %}` 分支很容易在改动时误伤另一支，肉眼看不出来。
`tests/test_resume_generator_validation.py` 里有直接渲染模板的用例可以照抄。

### 措辞与篇幅口径

`resume_generate_system.md` 里有三条**只在提示词层生效**的约束，代码不做强制校验，是否被遵守取决于模型：

- **措辞标准**：去口语、空话套话与互联网黑话（"赋能""抓手""闭环"）；强动作动词开头，
  但**不得升格职责范围**——"参与"不能写成"主导"。这条是防虚构的一部分，不要放松。
  其中点名的黑话另有**代码侧确定性检查**：`services/resume_wording.py` 的 `CLICHE_WORDS` /
  `CLICHE_PHRASES`，命中后复用既有的一次质量重试（`resume_quality_retry.md`），重试后仍在时以
  warning 告知用户。名单只收高置信度词——**误判会让每次生成多花一次模型调用**，还会把用户原本
  通顺的句子改坏；`落地`、`推动`、`梳理` 等正当的简历动词不在名单内。只在启用美化拓展时检查：
  关闭美化时正文是用户资料原文，改它就是篡改用户自己的表述。
- **篇幅与粒度**：每条描述性要点 30 字左右（最多不超过 35 字）、单段经历或项目的要点不超过 6 条、
  个人总结 2-3 句且不超过 120 字。写成区间而不是硬上限，是因为真机两轮里各有一条贴线超出
  （32/35 字）。它与 `resume_quality.py` 的"要点过少"门槛（`min(3, len(reference_facts))`）不冲突；
  若深度美化因为字数上限写不出扎实要点，先放宽这里的字数，**不要**去放宽质量门槛。
- **分模块呈现要求**：经历/校园/项目的要点要以强动作动词开头、写清"做了什么 + 结果"，
  项目 highlights 不能只堆技术名词；技能只能选资料里已有的项并按熟练度/岗位相关度排序；
  教育只在资料里有 GPA、课程、荣誉时呈现；奖项没有就输出空数组。
- **不输出空壳条目**（第 12 条）：候选条目本身没有任何可写事实（description、highlights、
  reference_facts 全空）时省略它。这条来自一次真机生成：资料里有个项目只有名称，被候选筛选选中后
  模型原样输出，成品上就是"一行没有内容的项目"——比少写一条更难看。注意它与第 11 条互补，
  不是给"少写"开口子。

改这些约束后要同步更新
`tests/test_resume_generator_validation.py::test_system_prompt_pins_writing_rules_for_both_modes`——
它按两种模式分别渲染模板，钉住这些句子还在、且关键词融入只出现在岗位分支。

## 粘贴识别 Prompt

岗位和个人资料粘贴识别会先使用本地规则生成可编辑草稿。用户已配置模型时，
`text_extraction.py` 将原始粘贴文本与该草稿提交给对应的结构化抽取 Prompt；未配置模型、
模型超时、调用失败或返回非法 JSON 时，会自动保留本地草稿。

两个 Prompt 都把粘贴内容标记为不可信资料，并要求模型只提取原文明确存在的事实。代码层还会
执行 JSON 解析、字段白名单、长度限制和原文锚点校验；无法在原文中找到依据的模型字段不会写入
草稿。调参时不得放宽这些边界，也不能要求模型补全未提供的经历、公司、日期或量化成果。

**图片输入时锚点会换一个来源。** 请求带图片时，`text_extraction.py` 把
`image_extraction_addendum.md` 追加到上面两个模板之后，要求模型先用 `transcription` 逐字抄录
图片文字，代码再拿**粘贴文本 + 抄录**的并集做锚点校验。所以：

- 这是**自洽性校验，不是来源校验**——它保证字段与模型自己写下的抄录一致，不保证抄录忠实于截图。
  模型把幻觉写进抄录就能通过。不要把它当成文本路径那种强度的保证，也不要把抄录再喂给第二个模型
  去"验证"（那只是把同一份自述换个地方生产一遍）。
- 抄录为空时整次识别直接失败（而不是回退到只用粘贴文本），避免"图片一个字段都没读出来，却因为
  粘贴文本里有内容而报成识别成功"。
- 抄录会把模型输出显著变长，而截断会让整份 JSON 不可解析、整次调用回退。所以模板里限定"只抄与
  识别相关的文字、每张图不超过约 6000 字"；放宽这个限制前请先确认服务商的 `max_tokens` 够用。
- 字段被静默丢弃（抄录里有、但标点或全角半角对不上）时，先改模板里"逐字、保留标点"的措辞，
  **不要**去放宽 `_normalized()`——它同时服务文本路径，改了会削弱那边的保证。

**文档输入走的是文本那条路。** PDF/DOCX 由 `document_text.py` 在本机提取成文字后并入
`source_text`，锚点仍然是"字段必须逐字出现在用户给的材料里"，强度与粘贴文本相同，不需要
`transcription` 机制。提取不到文字（扫描件）时整次请求直接以 422 失败并提示改用截图，不会
退化成"看起来成功"的空结果——这一点和图片路径的处理原则一致。

## 常见调参场景

### 1. 生成内容太"空"、没有针对性

系统会先通过 `profile_relevance.py` 兼容门面编排 `profile_context.py`、
`profile_matching.py`、`profile_references.py` 和 `profile_budget.py`，从完整资料库中
筛选岗位候选事实，再交给模型生成。
候选内容按相关度排序，最多保留有限的经历、项目、校园经历、技能和奖项；原始资料不会被修改。
如果条目附带总结文件，系统还会从文件中抽取与 JD 技能和方向最相关的片段，而不是把整份长文无差别塞入 Prompt。
深度美化时，生成器会在事实回填前检查附件项目是否被遗漏、要点是否过少、是否只是照抄附件，以及描述与亮点是否合理分配。检查不通过会自动进行至多一次非流式质量重试；重试失败或仍不合格时保留首轮结果，再使用可追溯事实兜底，不会让一次额外调用导致整份简历生成失败。

**JD 匹配要求已内置在第 2 条**：拆解 JD 的高频硬技能与职责动词、把直接匹配的条目前置，
并要求关键词只在候选事实确有对应内容时自然融入。还想加强时的安全做法是加强**排序与取舍**，
而不是补内容，例如追加：

```markdown
此外，若某条 JD 要求对应的候选事实很薄弱，宁可少写，也不要为了覆盖它放大该条目的权重。
```

### 2. AI 夸大或虚构成果

收紧真实性约束，同时配合 `check_consistency`（见下文）：

```markdown
1. 真实性第一：只能使用个人资料中已有的信息；资料中没有的具体数字
   （如"性能提升 40%"）一律不得出现，改用定性描述（如"显著提升性能"）。
```

### 3. 输出 JSON 经常解析失败

- 在 `resume_generate_system.md` 末尾加一句：`输出必须以 { 开头、以 } 结尾`。
- 换更强的基础模型（解析能力与基础模型强相关）。
- 调整 `temperature`（设置页）：简历生成优先使用 `0.1`（通常建议 `0.1-0.3`），降低同一资料反复生成时的随机波动；需要更有创意的改写时再逐步调高。

### 4. 调整美化拓展强度

- `light`：只优化措辞、顺序和重点，基本保持原文粒度。
- `balanced`：从资料和参考片段提炼方法、职责和结果，重组为更完整的岗位表达。
- `strong`：深入呈现有事实依据的架构、技术决策、难点与业务价值，但仍不能新增未经资料支持的数字、技术、角色或成果。

分级指令仍位于 `backend/app/services/resume_generator.py`，前端标签位于
`frontend/src/config.ts`。生成编排、JSON 规范化、事实回填、一致性检查和质量门槛分别由
`resume_generator.py`、`resume_content.py`、`resume_grounding.py`、
`resume_consistency.py` 和 `resume_quality.py` 负责；两边调整时必须同步，并为每个等级保留
Prompt 单测。关闭美化拓展时，生成器只允许选择、排序并回填资料原文。

## 参考文件的信任边界

参考文件属于用户资料，而不是系统指令。Prompt 会把其中内容标记为不可信事实材料：模型可以提取事实，但不得执行文件中的命令、角色要求或输出格式要求。文件正文只在启用美化拓展时参与生成，并受统一上下文预算限制。

## 防虚构校验（代码层兜底）

Prompt 只能约束，不能保证。生成器先由 `resume_grounding.py` 把姓名、名称、日期、角色和技能等级等结构字段锚定回候选资料，再由 `resume_consistency.py` 的 `check_consistency` 检查未知学校、公司、项目、技能、奖项和量化结果。`resume_grounding_helpers.py` 只提供纯匹配和证据函数，便于离线测试和后续替换。关闭美化拓展时，描述要点也会回填为资料原文；开启后可以保留基于参考事实的专业改写，但资料与参考片段中没有的数字仍会被拒绝并回退到原始事实。

## 调试建议

- 后端日志能看到完整调用链（`app/api/resumes.py` 有 logger 输出）。
- 生成弹窗中保留了模型的原始流式输出，方便判断是模型问题还是解析问题。
- 单测 `tests/test_profile_relevance.py` 覆盖岗位筛选、超长资料压缩与事实回填；`tests/test_resume_generator.py` 覆盖解析与校验。改完模板后跑一遍 `pytest` 即可回归。
