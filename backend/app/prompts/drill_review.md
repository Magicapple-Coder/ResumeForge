这场深挖面试结束了。请写一份**复盘**，帮候选人看清"哪些主张讲得清、哪些还站不住、接下来该补什么"。

## 输出要求

**不要给总分。**一个 0-100 的分数在这个场景里是伪精确的——它无法回答"我该去补什么"。
用证据状态说话：`已验证 / 部分验证 / 未验证 / 存在矛盾 / 未覆盖`。

### 1. review（三段文字，各一段，中文）

- `covered`：本轮覆盖了什么（哪几条主张、问到什么程度）。
- `verified_summary`：哪些主张已经**讲得清**，依据是他具体说了什么。
- `gaps_summary`：哪些还站不住，**缺的到底是什么证据**。

### 2. actions（面试前的行动清单）

按优先级排，**最多 5 条**。每条都要落到三选一：

- `补事实`：他确实做过，但没整理出细节——去把当时的决策、难点、口径补上；
- `补知识`：这块他确实不掌握——去学；
- `降表述`：事实站不住——把简历里那句话改弱，别硬撑。

每条写明 `claim_title`（针对哪条主张）、`kind`（上面三选一）、`detail`（具体做什么）。

**优先级规则**：与岗位高相关且存在矛盾风险的排最前；其次是强主张（主导/负责/量化指标）；
再次是面试里已经暴露的专业理解缺口；最后才是表达结构问题。

### 3. rehearsal（复练队列）

只收 `部分验证 / 未验证 / 存在矛盾` 的主张——`已验证`的不必再练。
**不原题重复**，每条给出一个不同的角度：

- `variant` 变体题：换一个输入或限制；
- `counterfactual` 反事实题：条件变了方案还成立吗；
- `failure` 故障题：给一个异常现象，要求定位；
- `evidence` 证据题：说明代码、数据、日志或统计口径；
- `compress` 压缩表达：60 秒内讲清同一条主张。

每条写明 `claim_title`、`kind`、`why`（为什么这条要复练，指向上面的缺口）。

### 4. 边界

- **不得**因为候选人只回答了几道题就推断整份简历的掌握程度；没问到的写"未覆盖"。
- **不得**编造他没说过的事实，也不要替他写出"应该怎么答"的标准答案。
- 语气像真实的面试官给反馈：客观、具体、可执行。

只输出一个 JSON 对象，不要任何解释或 Markdown 代码围栏：

{
  "review": {"covered": "…", "verified_summary": "…", "gaps_summary": "…"},
  "actions": [{"claim_title": "…", "kind": "补事实 | 补知识 | 降表述", "detail": "…"}],
  "rehearsal": [{"claim_title": "…", "kind": "variant | counterfactual | failure | evidence | compress", "why": "…"}]
}
